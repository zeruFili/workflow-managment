3. Authentication & Authorization

F-AUTH-001: User Login POST /api/v1/auth/login

Roles: Public

Input: username (3-100 chars), password (8-128 chars)

Output (200): { accessToken, refreshToken, user: { id, username, name, role } }

Business Rules: Account must be active. Rate limit: 5 failed attempts per 15 min per IP; 5th failure locks account 30 min. Password hashed with bcrypt (cost 12). If force_password_change = true, response includes forcePasswordChange: true.

Audit: login_success / login_failed / account_locked. IP + user agent logged.

F-AUTH-002: Token Refresh POST /api/v1/auth/refresh

Roles: Public (cookie-based)

Output: { accessToken, refreshToken } (rotated)

Business Rules: Old refresh token revoked on use. Expires after 7 days. If revoked token reused → revoke ALL tokens for that user (fraud detection). Access token claims: { sub, role, iat, exp }.

F-AUTH-003: Logout POST /api/v1/auth/logout

Auth: Bearer token | Output: 204 No Content

Revokes specific refresh token. Optional { allDevices: true } to revoke all user tokens.

F-AUTH-004: Forgot Password POST /api/v1/auth/forgot-password

Input: { email } | Output: Always returns success message (prevents enumeration).

Generate unique token (hashed), expire 1 hour, send email with link.

F-AUTH-005: Reset Password POST /api/v1/auth/reset-password

Input: { token, newPassword }

Business Rules: New password must differ from last 3. Must include uppercase + lowercase + digit + special char (8-128 chars). Token single-use; all existing refresh tokens revoked. Mark force_password_change = false.

F-AUTH-006: RBAC Middleware

Every endpoint checks JWT role claim against allowed roles. CEO inherits all GM permissions.

Error Responses: 401 TOKEN_EXPIRED → refresh token; 403 FORBIDDEN → role not permitted; 401 INVALID_TOKEN → re-login required.

4. Marketing Functions

F-MKT-001: Create Customer Request POST /api/v1/customer-requests

Roles: marketing_lead ceo

Input: customerName (1-500), customerPhone (E.164), customerEmail (optional), customerAddress (1-2000), category (enum), serviceDescription (1-5000), preferredStartDate (ISO 8601, not past), budget (positive, max 2 decimals), notes (max 5000).

Output (201): Full CustomerRequest object with status: "new".

Business Rules: BR-MKT-001: Status always new. BR-MKT-002: Creator from auth context. BR-MKT-003: Phone validated E.164. BR-MKT-004: preferredStartDate cannot be past.

F-MKT-002: View Customer Requests (List) GET /api/v1/customer-requests

Query: status, category, search (max 200), sortBy, order, page, limit (1-100).

Marketing Lead sees only own requests; CEO sees all. Default sort: newest first.

F-MKT-003: Update Customer Request PATCH /api/v1/customer-requests/{id}

Cannot update if status is scheduled or closed (409). Only creator or CEO. Budget changes >50% flagged.

F-MKT-004: Delete Customer Request DELETE /api/v1/customer-requests/{id}

Cannot delete if transferred to paid customer (409). CEO can force-delete; Marketing Lead only own.

F-MKT-005: Transfer to Paid Customer POST /api/v1/paid-customers (multipart/form-data)

Input: sourceRequestId (UUID), paymentNote (max 2000), proofFiles (1-5, image/PDF, max 10MB each).

Notifications: ALL finance_officer + ALL ceo. Type: payment_submitted. Title: "New Payment Submitted".

F-MKT-006: Respond to Finance Clarification POST /api/v1/paid-customers/{id}/clarify

Only when status = request_clarification. Resets status to pending. Multiple review cycles allowed.

F-MKT-007: View Paid Customers (Marketing View) GET /api/v1/paid-customers

Marketing Lead sees only records they transferred (unless CEO).

5. Finance Functions

F-FIN-001: View Finance Review Queue GET /api/v1/paid-customers

Roles: finance_officer ceo general_manager

Tab navigation: Pending | Verified | Rejected | Clarification | CEO-Transferred. Each with count badge.

F-FIN-002: Verify Paid Customer Payment POST /api/v1/paid-customers/{id}/verify

Input: action (approve|reject|request_clarification), message (required for reject + clarification, max 5000).

Notifications: Marketing Lead who transferred. Type: payment_reviewed. Title: "Payment {Approved|Rejected|Needs Clarification}".

F-FIN-003: View CEO-Transferred Payments GET /api/v1/paid-customers?transferredBy={ceo-uuid}&status=pending

Records transferred directly by CEO (no Marketing involvement).

F-FIN-004: View Payment Verification History GET /api/v1/paid-customers/{id}/verification-history

History immutable. Sorted chronologically ascending.

6. CEO Functions

The CEO has full access to all system functions, including those of the General Manager. The CEO is the only role with user management privileges and the ability to override finance decisions.

F-CEO-001: User Management — List Users GET /api/v1/users

Query: role, status (active|inactive|deleted), search, sortBy, order, page, limit.

CEO cannot delete own account. Soft-deleted users excluded by default.

F-CEO-002: User Management — Create User POST /api/v1/users

Input: username, name, email, password (complexity required), role (cannot be ceo), phone (optional, E.164).

force_password_change = true for new users.

F-CEO-003: User Management — Update User PATCH /api/v1/users/{id}

Cannot change own role or set own status to inactive/deleted. Role change requires confirmation.

F-CEO-004: User Management — Soft Delete User DELETE /api/v1/users/{id}

Soft delete only — records preserved for audit. All refresh tokens revoked. Assigned tasks remain but show "Deleted User".

F-CEO-005: View Approved Paid Customers GET /api/v1/paid-customers

CEO sees ALL records regardless of creator. Full visibility across all statuses.

F-CEO-006: Perform Finance Functions

CEO inherits all finance officer capabilities. Can override any finance decision including changing already-approved payments.

F-CEO-007 through F-CEO-022 cover: CRUD Data Collector Tasks, Review Data Collector Tasks, CRUD Designer Tasks/Job Postings, Assign Designer to Task, View Assigned Designers, View Designer Applicants, Review Designer Application, Review Designer Phase Submission, Final Evaluation/Rating, Update Designer Rating, View Designer Performance, View Paused Designer Tasks, CRUD QS Tasks, Assign QS User, Review QS Evaluation, and View QS Review History. See the full specification above for complete details on each function.

7. General Manager Functions

The General Manager has all designer management access but is excluded from User Management and Finance override capabilities.

F-GM-001: All Designer Management Access

Inherits F-CEO-009 through F-CEO-022. Excludes User Management and Finance override.

Route Restrictions: /users → DENIED (403). Cannot override already-approved finance decisions. Full access to designer assignments, applications, phase reviews, ratings, QS tasks, and Data Collector Tasks.

8. Quantity Surveyor Functions

F-QS-001: View Assigned QS Review Tasks GET /api/v1/qs-review-tasks

QS sees only tasks assigned to them. Tasks highlighted as "New" if status: "pending_review" and not viewed.

F-QS-002: Accept and Begin Review PATCH /api/v1/qs-review-tasks/{id}/status

Transition: pending_review → in_review. Opening detail automatically triggers this.

F-QS-003: Submit QS Evaluation POST /api/v1/qs-evaluations

Input: taskId, costValue (positive, 2 decimals), evaluationNotes (10-5000), recommendation (recommend_approval|recommend_revision).

F-QS-004: View QS Review History and Decisions GET /api/v1/qs-evaluations

QS sees own evaluations and decisions. Sorted newest first.

9. Designer Functions

Designers work through a 4-phase submission workflow: Case Study → Design Stage → Rendering → Final Stage. Each phase must be approved before the next unlocks.

F-DSGN-001: View Assigned Designer Tasks GET /api/v1/designer-tasks

Designer sees only tasks assigned to them. Phase progress from designer_phase_history.

F-DSGN-002: Submit Case Study Phase POST /api/v1/designer-tasks/{id}/phases/case_study/submit

First phase — no prerequisites. Input: note (5-5000), screenshot (optional).

F-DSGN-003: Submit Design Stage Phase POST — Phase 2

Requires Case Study approved.

F-DSGN-004: Submit Rendering Phase POST — Phase 3

Requires Design Stage approved. Screenshot recommended for 3D render evidence.

F-DSGN-005: Submit Final Stage Phase POST — Phase 4

Requires Rendering approved. Screenshot MANDATORY. After approval, task completed and eligible for rating.

F-DSGN-007: View Open Job Postings GET /api/v1/designer-tasks?isPublic=true&assignedTo=null

Designers browse public, unassigned tasks with story points and deadline.

F-DSGN-008: Apply for Job Posting POST /api/v1/designer-task-applications

Cannot apply twice for same task (409). Status always pending on creation.

F-DSGN-006, F-DSGN-009 through F-DSGN-012 cover: View Feedback/Approval History, View Application Status, View Personal Performance Ratings, Upload Telegram Screenshot Evidence, and Update Phase Notes.

10. Site Engineer Functions

F-SE-001: View Assigned Site Tasks GET /api/v1/tasks?taskType=site_engineer

Status filter tabs: All, Pending, In Progress, Completed, Incomplete, Rejected. New tasks highlighted with "New" badge via IntersectionObserver.

F-SE-002: Update Task Status PATCH /api/v1/tasks/{id}/status

Valid transitions: pending → in_progress → completed → incomplete. Cannot set rejected.

F-SE-003 through F-SE-005 cover: Update Task Description, Upload File Attachments (JPG/PNG/PDF/DOCX/XLSX, max 10MB), and View Task Approval Status.

F-DC-003: Submit Task Evidence POST /api/v1/data-collector-tasks/{id}/submissions

13. Notification System

13.1 System Overview

Two tiers: Server-side — PostgreSQL notifications table (one record per recipient per event). Client-side — CustomEvent bus via window.dispatchEvent(...) for real-time badge updates.

13.2 Notification Lifecycle

Action occurs → Server creates 1 notification per recipient role user
    → WebSocket push + DB storage
    → Frontend CustomEvent → badge count update
    → User views → PATCH /api/v1/notifications/{id}/read
    → Read notifications persist with readAt timestamp

14.2 Rating Statuses

approved — Finalized, visible to designer. in_review — Under review, not yet visible. rejected — Error in evaluation.

15. Audit Trail System

15.1 Overview

Every state-changing operation creates an immutable audit log entry capturing who did what, to which entity, at what time, with a JSON diff of changes.

15.3 Audited Actions

Auth: login_success, login_failed, account_locked, logout, token_refresh, password_reset
Users: user_created, user_updated, user_deleted, user_role_changed, user_status_changed
Finance: payment_submitted, payment_verified, payment_rejected, payment_clarification_requested, payment_override
Tasks: task_created, task_updated, task_deleted, task_status_changed, task_assigned, task_reviewed
Designer: designer_task_created, designer_phase_submitted, designer_phase_reviewed, designer_rating_created
System: system_config_updated, audit_log_exported

15.6 Retention & Compliance

Default retention: 365 days (configurable). Archive to S3 Glacier after retention. GDPR: PII masked in changes diff. Chain of custody via sequential IDs and timestamps. Periodic hash verification for integrity.
